= Descriptions
include::_fpsot-terms.adoc[]

Toute {abbr-api-first} a une description que lisent les personnes et les outils.
La description est le contrat entre le serveur et ses clients.

[[API-020]]
*API-020.* Toute {abbr-api} DOIT avoir une description selon la spécification OpenAPI, version 3.2 ou 3.1.
Une nouvelle description DEVRAIT employer link:https://spec.openapis.org/oas/v3.2.1.html[OpenAPI 3.2.1] ou une version corrective 3.2 ultérieure.
Une description PEUT employer link:https://spec.openapis.org/oas/v3.1.2.html[OpenAPI 3.1.2] ou une version corrective 3.1 ultérieure.
Des générateurs courants, comme celui de Quarkus, produisent encore la version 3.1.
La description DOIT couvrir chaque opération, paramètre, en-tête, corps de requête et réponse de l’{abbr-api}.
OpenAPI est le format commun des outils d’{abbr-api}.
Une description complète permet à n’importe qui de produire un client, un test ou une page de documentation.

[[API-021]]
*API-021.* Une spécification de domaine DOIT publier la description de chaque {abbr-api} qu’elle définit, avec son texte normatif.
Cette description publiée est normative.
Un serveur DOIT s’y conformer, et son intégration continue DEVRAIT le vérifier.
Une description produite à partir du code PEUT aider, mais le serveur NE DOIT PAS contredire la description publiée.
Les acheteurs et les autres équipes construisent selon le contrat publié, pas selon un serveur en particulier.

[[API-022]]
*API-022.* Un serveur en service DOIT servir la description de chaque version majeure à `/v<major>/openapi`, en {abbr-json-first}.
Un client et une passerelle trouvent alors la description sans rien demander à personne.

[[API-023]]
*API-023.* Les schémas DOIVENT employer link:https://json-schema.org/draft/2020-12[JSON Schema, version 2020-12], le dialecte par défaut d’OpenAPI 3.1 et 3.2.
Ils NE DOIVENT PAS employer le mot clé `nullable` d’OpenAPI 3.0.
Un schéma dans un dialecte normalisé fonctionne avec tout validateur {abbr-json} Schema, dans OpenAPI ou ailleurs.

[[API-024]]
*API-024.* Chaque opération DOIT avoir un `operationId` unique, un résumé et une description.
L’`operationId` DOIT avoir la forme d’un nom de champ.
Les générateurs de code transforment l’`operationId` en nom de fonction.
Le résumé et la description indiquent à une personne qui développe à quoi sert l’opération.

[[API-025]]
*API-025.* Chaque opération DOIT énumérer chaque code d’état qu’elle peut renvoyer.
Chaque réponse d’erreur DOIT renvoyer au schéma des détails de problème de la page xref:errors.adoc[Erreurs].
Chaque requête et chaque réponse de succès DEVRAIENT avoir un exemple.
Un client peut alors traiter chaque résultat que le serveur peut envoyer.

[[API-026]]
*API-026.* La description DEVRAIT donner ses résumés et ses descriptions en anglais et en français.
Elle PEUT le faire avec un fichier par langue, qui ne diffèrent que par leur texte.
OpenAPI n’a pas de champ pour une seconde langue.
Au Canada, les organismes publics doivent servir les deux communautés de langue officielle.

[[API-027]]
*API-027.* L’intégration continue DEVRAIT vérifier chaque description avec un outil d’analyse OpenAPI.
L’outil repère un champ manquant ou un renvoi brisé avant qu’un client le trouve.
